# ADR-003 — Программные backends: mock / wire / LPT

## Статус
Принят (2026-08-06).

## Контекст
Бизнес-ядро (`core::ops`) зависит только от абстракции `kr1878_core::backend::Backend`, но конкретные реализации (железо и тесты) принадлежат слою *Hardware* (`kr1878-programmer`). Нужны реальный LPT, эмуляция для тестов/CI и понятный путь до USB-моста — без нарушения слоистости (UI → Business → Protocol → Hardware).

## Решение
В `kr1878-programmer` реализованы три сущности:

- `MockBackend` — полностью in-memory `Backend` (стирание → `0xFF`), для юнит-тестов, CLI и CI без железа;
- `WireBackend` — адаптер: переводит `protocol::Device` (который уже умеет erase → write → verify) в `core::backend::Backend`;
- `LptTransport` — `protocol::Transport` на уровне параллельного порта (база `0x378`; инверсия BUSY(bit7)/ACK(bit6) по `HARDWARE_PROTOCOL`), используется вместе с `WireBackend`.

Прямой доступ к портам (`0x378/0x379/0x37A`) доступен на Linux/FreeBSD x86-64 (via `ioperm`+`inb`/`outb`); на остальных платформах любые LPT-операции возвращают типизированную ошибку «LPT backend unavailable», и сборка остаётся кроссплатформенной.

## Следствия
- `core::ops` не менялся; интеграционные тесты проходят end-to-end через `MockBackend`.
- Будущий USB-мост — просто реализация `Transport`, линейно подключаемая к `WireBackend`.
- Фактическая полярность линий на реальном железе LPT не проверена — помечена как требующая проверки.

## Альтернативы
- Реализовывать `Backend` напрямую в каждом транспорте: отвергнуто, т.к. дублировало бы драйвер состояния между `protocol::Device` и `programmer`.
