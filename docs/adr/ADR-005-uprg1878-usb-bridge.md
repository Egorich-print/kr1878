# ADR-005 — USB-мост по образцу официального `Uprg1878.exe`

## Статус
Принят (2026-08-11); реализован как `UsbBridgeBackend` в `crates/programmer/src/usb.rs`
(+ CLI `--backend usb`, desktop `usb`), требует верификации на реальном железе.

## Контекст
Официальный современный программатор Angstrom (`Uprg1878.exe`, Lazarus/Free Pascal
x86-64, символы не стрипнуты, есть DWARF) работает **не через LPT**, а по
**COM-UART 38400-8N1 через USB-мост**. Полное дизассемблирование обработчика
`BUTTON2CLICK` (0x100030560), локальных DWARF-переменных (`word_conf`, `txbuf[16]`,
`rxbuf[16]`), форм-ресурса `.lfm` и класса `TComPort` дало точный протокол — см.
`docs/HARDWARE_PROTOCOL.md` §7.

Это третий известный вариант "прошивальщика" alongside `E03_PROG`/`P_WMCT`
(LPT bit-bang) и наш собственный `Mock/Sim/LPT`. Отличается:

1. единица обмена — блок ровно 16 байт, не битовый поток;
2. подтверждение — байт `'R'` (0x52), приём «до тишины» (последний байт == 'R'),
   а не проверка уровня ACK;
3. program-память берётся из `.sav` с пропуском **256 слов (0x100 в `file of Word` =
   512 байт) заголовка** (файлы Angstrom/TESSA несут 256-словный заголовок);
4. data EEPROM (64 байта) и program пишутся двукратно (фазы B/E), **без read-back**;
5. конфигурация — 16-бит слово, биты утроены (RDE/OT1/OT2 по даташиту, §7.5),
   в отдельном блоке (Фаза D);
6. «Верификация» = повторная запись, инструмент никогда не читает содержимое МК.

## Решение
LPT-протокол (§1–5) и USB-протокол (§7) — **независимые каналы** одного
программатора:

- существующие `LptTransport`/`WireBackend`/`MockBackend` не тронуты;
- добавлен `UsbBridgeBackend` (отдельная реализация `Backend`, не через
  `Transport`/`WireBackend` — протокол полностью другой), реализующий §7.3:
  - `serialport` 38400-8N1, write-timeout 1000 мс, per-block read-timeout;
  - блоки 16 байт + `'R'`-подтверждение (drain-до-тишины, таймаут 80 мс / 1000 мс для config);
  - фазы: sync → data×2 (64 байта) → program (128×16) → config (hi/lo) → program повтор;
  - `read_program`/`read_data`/`read_config` возвращают **shadow-image** (протокол
    не имеет read-back; «верификация» = повторная запись), поэтому
    `ops::program_with` и `ops::verify` работают поверх USB-бэкенда без изменений;
  - config-слово собирается из `GeneratorMode` + флага задержки (`config_word`).
- `core` не изменялся: добавлена ещё одна реализация `Backend`.
- в `kr1878-file-format` добавлен `read_sav_uprg` — чтение официальных `.sav`
  с пропуском 256-словного заголовка.

## Следствия
- Появляется путь совместимого программирования реального МК через дешёвый
  USB–UART-мост (FT232/CH340) без покупки фирменного устройства.
- CLI: `kr1878 write --backend usb --port <port> [--gen rc|internal|quartz-high|quartz-low] [--no-delay]`
  и `kr1878 ports` (список COM-портов, аналог `GetSerialPortsList`).
- read/verify над USB-мостом запрещены на уровне CLI/UI (нет read-back) — явная ошибка.
- **Требует верификации на реальном программаторе** [GAP]:
  - содержимое первого (sync) блока не инициализируется хостом; Rust-реплика шлёт
    `0xFF×16` — надо подтвердить, что устройство отвечает `'R'` на любой блок;
  - фаза D шлёт 16 байт, из которых осмысленны только первые 2 (конфиг-слово
    big-endian), остальные — стековый мусор; предположение, что устройство читает
    только первое слово, требует проверки;
  - тайминг «тишины» 80 мс и межблочные паузы <80 мс на реальном устройстве.

## Альтернативы
- Переписать `protocol` под блочный обмен: отвергнуто — LPT-путь остаётся целевым
  и покрыт тестами; дублирование логики дешевле, чем ломать проверенную архитектуру.
- USB-мост как `Transport` → `WireBackend` (ADR-003): отвергнуто, т.к. Uprg1878
  не передаёт LPT-битовые сигналы, а использует собственный блочный протокол;
  `Transport`/`WireBackend` неприменимы напрямую.
